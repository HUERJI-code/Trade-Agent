## 当前模型如何知道工具、何时调用

旧版 CLI 把业务规则和七字段 JSON schema 发给模型，由 Python 校验计划并调用业务函数。新版网页通过 `ChatOllama.bind_tools(QUERY_TOOLS)` 把三个工具的名称、说明、参数类型发送给模型：`run_metric`、`clarify_query`、`unsupported_query`。

模型结合问题、规则和工具说明提出调用。程序仍会检查日期、国家、指标和分组与用户问题是否一致，再通过 `run_metric.invoke` 执行。工具目录不是模型目录；具体模型由配置文件选定，LLM 不扫描 Python 文件，也不自行选择另一个模型。明确越界或缺日期等情况仍由入口检查提前处理。

`Annotated` 把参数解释放进工具 schema。只有 country、dimension 的字符串 `"null"` 会规范化为真正的 null；明确指定德国时返回 null 仍会被拒绝，因此不会悄悄去掉国家筛选。参数校验失败会反馈具体原因，最多重试一次。旧 JSON 协议与新工具调用协议分别生成提示，避免互相矛盾。

## LangGraph 带来的变化

网页流程：React → FastAPI → 恢复会话 → 补齐省略条件 → 模型提出工具调用 → 校验 → 只读 SQL → 模型组织回答 → 校验回答 → 保存会话。

| 问题 | 当前行为 |
|---|---|
| 2019年德国销售额是多少？然后问“那法国呢？” | 同一会话继承年份和指标，改查法国 |
| 再问“订单数呢？” | 继承法国和2019年，查询去重订单数 |
| 新会话直接问“那法国呢？” | 没有旧条件，需要澄清 |
| 德国销售额是多少？然后补“2019年” | 合并明确补充的时间，再执行查询 |
| 2019年德国销售额比2018年增加多少？ | 当前仍要求单一时间范围；框架没有自动扩展同比工具 |
| 同时在两个窗口提交分析 | 会话各自保存；第二个推理请求可能收到429，当前仍单次推理 |

会话存在 `.runtime/conversations.sqlite3`，不是写入业务 MySQL。当前是本机单用户应用，不是远程多租户系统。

## 训练实际结果

采用标准 `datasets + Transformers + PEFT + TRL SFTTrainer` Python 流程。基座 `Qwen/Qwen3-8B` 固定 revision `b968826d9c46dd6066d109eabc6255188de91218`。NF4 QLoRA、BF16 计算；rank 8、alpha 16、dropout 0.05、学习率 1e-4、micro batch 1、梯度累积16，2轮共88个优化器步骤。

训练698条、验证206条、测试206条；只监督 assistant 回答与模板结束部分。全部样本检查长度与标签，无静默截断。曾按用户要求暂停并恢复；Windows 状态文件短暂占用导致一次中断，日志写入已增加短暂重试，未保存步骤重算。

| 观察项 | 结果 |
|---|---|
| 第1轮验证损失 | 0.111015 |
| 第2轮验证损失 | 0.013877 |
| 训练峰值已分配显存 | 约7.082 GiB |
| 最终adapter权重 | 87,360,584字节 |
| 优化器更新 | 88步 / 2 epochs |

[训练曲线](../outputs/training/answer_style_qwen3_8b_sft_v1/loss_curve.png)。损失衡量参考回答 token 的预测程度，不是完整问答准确率；首轮固定超参数没有经过搜索，不能声称最优。

## 回答评估结果

同一份206条测试数据、同样提示、temperature=0、seed=42、context=4096、最多384个生成token。保留模型原始回答，不用生产回退答案替代失败样本。

| 指标 | 原模型 | LoRA模型 |
|---|---:|---:|
| 全部 206 条自动检查通过 | 98.06% | 94.66% |
| 正常结果 148 条自动检查通过 | 98.65% | 99.32% |
| 主指标按要求加粗（152 条适用） | 0 / 152 | 152 / 152 |
| 毛利率先说明汇总计算口径（18 条适用） | 0 / 18 | 18 / 18 |
| 去空白后与参考回答完全一致 | 0 / 206 | 99 / 206 |
| 输出不超过 220 字 | 202 / 206 | 206 / 206 |

结论：目标表达风格有明显改善，正常结果的自动检查通过率略升，但全部样本的自动检查通过率下降，不能称为全面能力提升。自动规则不覆盖完整语义；数字集合匹配、参考全文匹配也不等于业务正确率。

数据中同一事实有两种问法，因此206条不是206个独立事实；部分数据为已标注的模拟边界。基线是旧Ollama量化模型，候选是固定HF基座合并后重新量化，二者权重来源与量化流程不完全一致。这是部署效果对比，不能把全部差异严格归因于LoRA。

## 人工检查发现与部署边界

候选原始回答有11条未通过规则检查：3条澄清、3条不支持请求、4条包含思考标记的异常输出，以及1条并列排名漏掉“估算”。其中不支持请求曾编造未提供的欧元毛利；这属于实际模型错误。完整逐条样例见 [失败样例复核](LoRA失败样例复核.md)。

生产图中的澄清与拒绝由程序返回，不交给回答模型。成功查询的回答还会检查数值、国家、估算标记等；异常时保留数据库结果并回退原有文案。该检查也不是任意自然语言事实的完整证明。

最终现场16个场景全部查询/流程检查通过，含六指标、追问、补条件、三种分组和国家极值。12条可生成回答的成功查询中，10条使用LoRA回答，2条触发模板回退。场景含训练年度，不能当作独立泛化评测。

反事实测试：六个问题各使用原context和替换context，共12条通过自动检查，含负毛利、替换金额、替换毛利率和计数。模型能在这些样例中跟随当前输入数值，但不能据此证明所有新问题都会正确。

离线测试：234项通过；1条Starlette/AnyIO弃用提示，不影响本轮功能。网页实际验证毛利率回答与加粗效果，并能继续追问订单数。

## 合并与部署过程

整模型CPU合并曾遇到meta占位张量和高内存阶段退出，最终采用逐层加载：将每个真实线性层及其训练后的A/B交给标准PEFT `merge_and_unload(safe_merge=True)`，转换FP16并分片写出。252个目标层、399个完整张量、18分片全部核对齐全；七种目标层加两个未训练层共9项逐元素核对通过。

本机Ollama0.33.3直接导入Safetensors实际返回“不支持Qwen3ForCausalLM”，因此改用官方llama.cpp b6500转换F16 GGUF，再量化Q4_K_M、导入Ollama。固定commit为`a7a98e0fffed794396b3fbad4dcdbbc184963645`，Windows CPU工具ZIP核对官方SHA-256。导入沿用原Ollama Qwen3工具聊天模板。
