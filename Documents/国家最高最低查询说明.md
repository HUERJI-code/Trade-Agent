# 国家最高／最低查询扩展

修复问题：输入“2019年哪个国家销售额最高？”时，旧版本的 `agent/service.py` 把“最高”作为不支持词提前拒绝；不是 MySQL 没有数据，也不需要通过 LoRA 微调修复。

现在支持明确年份或中文年月中的国家指标最高／最低，例如：

- 2019年哪个国家销售额最高？
- 2019年销售额最高的是哪个国家？
- 2019年3月哪个国家毛利率最低？
- 2019年哪个国家订单数最多？
- 2019年哪个国家销量最少？

已支持的指标仍是销售额、毛利、毛利率、订单数、活跃客户数和销量。未写时间仍澄清；今年／去年等相对时间仍要求明确日期。当前扩展不处理 Top N、多国排除条件、产品排名或多指标比较，不能把这些条件丢弃后回答另一个问题。

## 一次查询的处理过程

1. `agent/ranking.py` 的 `parse_country_extreme()` 用完整句式识别指标、最高／最低和日期，构造 `CountryExtremePlan`。没有完整匹配就交回原有流程。
2. `agent/service.py` 调用原来的 `run_metric()`，固定按全部客户国家分组。业务字典、只读账户和 SQL 校验仍生效。
3. `compare_countries()` 取得完整分组结果后，使用 Decimal 按汇总指标值比较。SQL 保持真实的分组查询，排序在 Python 中完成；查询结果中的 ranking.method 明确记录这一点。
4. 并列最高／最低全部列出；空指标不参与比较；触及 SQL 返回上限则拒绝判断极值；缺少数据覆盖时不声称有最高国家。
5. `render_result()` 写出中文结论，React 展示全部国家的有序表格、图表和排序条件。只比较所选期间有交易、指标可计算的国家，不把没有交易的国家擅自补成零。

明确句式使用规则解析，不调用本地模型。返回 `planner_source=country_ranking_rule`、`model=null`、`usage=[]`，审计日志也记录来源。模型自然语言主流程继续使用原有七字段 schema；扩展计划的 sort_order 由代码生成，不接受模型额外字段。

## 如何读新增代码

`agent/ranking.py` 中，METRIC_NAMES 将中文指标映射为批准的指标 ID；CountryExtremePlan 继承 QueryPlan，沿用日期和工具参数，额外保存排序方向；re.fullmatch 要求整句匹配，以免忽略用户额外条件；Decimal 保留十进制精度；两次稳定排序让同值国家按名称排列；winners 保留所有并列国家。

在 `agent/service.py` 中搜索 CountryExtremePlan，可以依次看到前置识别、计划来源标记、完整结果比较、答案生成与审计。前端搜索 result.ranking，可以找到排序条件和规则来源说明。

## 验证与结果

全量自动化测试：**220 passed**，其中本次新增 21 项测试。涵盖正常句式、缺时间、额外条件拒绝、数值与字符串排序差异、并列、空值、大数精度、截断拒绝、只读工具调用和真实 MySQL。

真实 MySQL 对该问题返回：**美国，2019 年估算销售额 10,133,066.38 美元**。共比较 8 个有交易国家；同一结果中的德国为 1,874,921.45 美元，与已有对账一致。

已重启本机 FastAPI 并重新构建 React。HTTP 实测结果保存于 `Documents/国家极值查询验证.json`；浏览器提交用户原问题后，已核对最高国家、8 行降序表格、对应柱形图及规则来源提示。

此次属于查询能力扩展。没有改动模型配置、提示词或权重，没有启动调参或 LoRA；原来的“调参前停止”要求继续有效。`调参前状态记录.json` 保留上次基线，因此服务文件指纹发生变化是本次功能修复造成的，不覆盖历史记录。
